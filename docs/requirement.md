# 需求分析 —— 题目09：测试车队日志策略的申请、审批、分批发布与结果核查

## 1. 业务背景

车云研发团队需要临时调高测试车辆诊断日志上报频率排查问题，但不得一次性对全车队发布。
流程：研发提出配置申请 → 负责人审批 → 运营先向2台试点车发布 → 试点结果明确后推广剩余3台 →
车端上报回执 → 负责人核查后完成；异常时停止活动；活动结束后可批准“恢复原设置”形成新一轮下发。

## 2. 角色

| 角色 | 账号（预置） | 能力 |
| --- | --- | --- |
| 研发申请人 | 张研发 | 创建申请（原因+5台车+新间隔）、修改被退回申请、重新提交 |
| 审批负责人 | 李负责 | 批准/退回（不能自审）、试点失败时决定停止、全部成功后记完成、批准恢复 |
| 发布运营 | 王运营 | 发起试点(选2台)、确认推广(剩余3台)、停止活动、发起并执行恢复 |
| 模拟车辆 | V1~V5（令牌鉴权） | 拉取最新已发布配置、上报成功/失败回执；模拟器页面可控在线/离线 |

预置：5台测试车，初始间隔均为 60 秒；间隔合法范围 10~300 秒；V1 在线、V2 离线（演示用）。

## 3. 状态机

### 活动（Activity）

```
draft --提交--> submitted --批准--> approved --发起试点--> piloting
   ^                |                  |
   +----退回--------+                  +--试点车超时--> pilot_paused --负责人/运营停止--> stopped
                                      |
                       试点2台全部成功 --运营确认推广--> expanding --全部5台成功--负责人记完成--> completed
任何 piloting/pilot_paused/expanding --运营/负责人停止--> stopped
stopped(有已发布配置) --运营发起恢复--> restore_requested --负责人批准--> restore_approved
                     --运营执行恢复--> restoring --全部恢复成功--负责人确认--> restored
```

### 车辆下发记录（Publish）

`published(已下发) → success(成功回执) | failed(失败回执) | timeout(60s无回执)`
- timeout 后收到当前版本 success → 更新为 success 并保留超时历史（late 标记）。
- failed 不改变该车已生效值。
- 每车版本号递增（含恢复下发）；期望值 = 最新下发的 target；已生效值 = 车辆当前实际间隔。

## 4. 核心业务规则（对照题面条款）

| # | 规则 | 来源条款 |
| --- | --- | --- |
| R1 | 申请必含原因、5台车、新间隔(10~300)；审批人≠申请人；退回可改再提交；批准后参数不可改 | 规则1 |
| R2 | 同一车队同时只允许一个未结束活动；试点恰好2台，其余车辆不得提前获得配置 | 规则2 |
| R3 | 两台试点均成功才可确认推广；试点失败/超时则暂停推进，不得绕过 | 规则3 |
| R4 | 车辆只取得面向自己的最新已发布版本；每车版本递增；期望值与生效值分存 | 规则4 |
| R5 | 回执须令牌鉴权且版本匹配；重复成功不重复记账；旧版本不能覆盖新版本；未知版本/跨车回执拒绝并记录 | 规则5 |
| R6 | 发布60秒无有效回执标超时（教学时钟可配置并注明）；当前期望版本迟到成功可更新并保留超时历史；失败不改生效值；已停止活动不因迟到回执重启 | 规则6 |
| R7 | 停止仅阻止未下发部分，不抹掉已发布/已生效记录；恢复需负责人批准，按各车活动前值创建新版本 | 规则7 |
| R8 | 全部5台确认成功才可记完成；恢复需全部确认才可记恢复完成；逐车可核查发布前值/期望值/生效值/成败/未确认 | 规则8 |

## 5. 异常与边界

- 并发：重复回执、重复发起试点/推广、推广与停止并发（事务保证唯一结果）。
- 权限：申请人不能自审；运营不能审批；车辆令牌决定身份，不能替他车回执。
- 网络：离线车拉取失败；超时后迟到成功；跨车/未知版本回执拒绝并留存诊断记录。
- 越权：请求不能指定“以谁的身份”操作，身份来自服务端会话。

## 6. 验收条件（可验证）

1. 正常推广全流程可操作并持久化，重启后可查。
2. 五组完整工作场景（题面“必须演示的完整工作场景”）均可实际操作并产生持久化结果。
3. 服务端包单测覆盖率 ≥85%，`go vet`、`-race` 通过。
4. 所有拒绝操作（越权、非法状态、重复操作）返回明确原因并记录。
